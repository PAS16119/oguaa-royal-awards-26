# Oguaa Royal Awards — Nomination Portal

**New to GitHub/Vercel/databases?** Skip straight to [`DEPLOYMENT_GUIDE.md`](./DEPLOYMENT_GUIDE.md) — a complete, click-by-click walkthrough written for someone who has never deployed a website before. The rest of this file is the shorter technical version.

A real, deployable version of the nomination system: Next.js on Vercel,
Postgres (Neon) for records, Vercel Blob for nominee photos. Manual-payment
only — codes are only ever generated by a logged-in Main Admin or Sales
Agent, after payment is physically confirmed.

## Architecture

- **Frontend + API:** Next.js 14 (App Router), deployed on Vercel.
- **Database:** Postgres via [Neon](https://neon.tech) (available directly, or through the Vercel Marketplace).
- **Photo storage:** [Vercel Blob](https://vercel.com/docs/storage/vercel-blob) — photos are compressed client-side, then uploaded to Blob; only the URL is stored in Postgres.
- **Auth:** Main Admin + Sales Agents. PINs are hashed with bcrypt server-side. Sessions are signed, httpOnly cookies (JWT via `jose`) — nothing sensitive ever reaches the browser.
- **Audit trail:** every code generation/use/void, agent creation/PIN reset/deactivation, login, and settings change is written to an append-only `audit_log` table.

## 1. Push this to GitHub

```bash
cd oguaa-royal-awards
git init
git add .
git commit -m "Oguaa Royal Awards nomination portal"
gh repo create oguaa-royal-awards --private --source=. --push
# (or create the repo on github.com and `git remote add origin ...` + `git push`)
```

## 2. Create a Postgres database (Neon)

- Easiest path: in your Vercel project, go to **Storage → Create Database → Postgres (Neon)**. Vercel automatically sets the `DATABASE_URL` env var for you.
- Or create a free database directly at [neon.tech](https://neon.tech) and copy its connection string.
- Either way, open the **Neon SQL Editor** (or `psql "$DATABASE_URL" -f lib/schema.sql`) and run everything in [`lib/schema.sql`](./lib/schema.sql) **once**. This creates all tables and seeds a default config row.

## 3. Add Vercel Blob storage

- In your Vercel project: **Storage → Create Database → Blob**. This automatically adds the `BLOB_READ_WRITE_TOKEN` env var — you don't need to copy it manually.

## 4. Import the project into Vercel

1. [vercel.com/new](https://vercel.com/new) → import the GitHub repo you just pushed.
2. Framework preset: **Next.js** (auto-detected).
3. Before the first deploy, add one more environment variable:
   - `SESSION_SECRET` — any long random string. Generate one with:
     ```bash
     openssl rand -base64 32
     ```
4. Deploy.

You should end up with three environment variables set on the Vercel project: `DATABASE_URL`, `BLOB_READ_WRITE_TOKEN`, `SESSION_SECRET`. `.env.example` shows the shape of each.

## 5. First run

1. Visit your live URL → **Committee & agent access** (footer link) → **Main Admin** tab.
2. No PIN exists yet, so you'll be prompted to create one — do this yourself, first, before sharing the link publicly.
3. Go to **Settings** and fill in the real opening/closing dates, price, and MoMo details.
4. Go to **Agents** to create sales agents/distribution points — each gets a unique Agent ID + one-time PIN to hand out.

## Local development

```bash
npm install
cp .env.example .env.local   # fill in real values

```

## Security notes

- PINs are **hashed with bcrypt** server-side — the plaintext PIN is only ever shown once, at creation/reset time, and is never stored or logged anywhere.
- Sessions are **signed httpOnly cookies**, verified on every API request server-side — a user can't fake a role by editing browser storage.
- All role checks (main-admin vs agent-scoped) happen in the API route handlers, not just in the UI.
- Still rotate PINs if you ever suspect one has leaked, and never commit `.env.local` or paste real secrets into the repo — they belong only in Vercel's environment variables.

## Notes on scale

Unlike the earlier Claude-artifact version, there's no ~20MB storage ceiling
here — Neon's free tier and Vercel Blob's free tier both comfortably handle
an event of this size, and you can upgrade either independently if the
anniversary turns out bigger than expected.
